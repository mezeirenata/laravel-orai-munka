## What We Have Built

### SQLite and training migration

The SQLite database file is `database/database.sqlite`. In Laravel's `.env`, `DB_CONNECTION=sqlite` selects SQLite. With `DB_DATABASE` empty, Laravel uses the project's default SQLite path.

The `create_trainings_table` migration defines:

- `id`: integer primary key generated by `$table->id()`.
- `name` and `trainer`: strings limited to 100 characters.
- `starts_at`: date and time.
- `duration`, `price`, and `free_spots`: unsigned integer columns; `free_spots` defaults to 0.
- `created_at` and `updated_at`: timestamps added by `$table->timestamps()`.

SQLite does not enforce unsigned integer constraints like some database engines. Request validation must still reject negative values where required.

### Training model

`app/Models/Training.php` represents a row in the `trainings` table. Laravel infers that table name from the model name. Its `$fillable` array lists fields that may be assigned through mass assignment, for example when creating a model from validated request data.

The `registrations()` method defines a one-to-many Eloquent relationship using `hasMany()`. Laravel conventionally expects the foreign key `training_id` on registrations.

### Factory and seeder

`database/factories/TrainingFactory.php` contains reusable sample values. `fake()->randomElement([...])` selects from training names, trainers, allowed durations, and allowed prices. `fake()->numberBetween(1, 20)` makes a typical training have available spots.

`database/seeders/TrainingSeeder.php` assembles the assignment's special groups:

- 17 ordinary future trainings from the factory.
- 3 future trainings whose `free_spots` are overridden to 0 using `state()`.
- 2 past trainings whose `starts_at` is overridden.

The line `// Training::query()->delete();` is commented out. Running the seeder repeatedly without clearing records first will add duplicates. For repeatable setup, the project eventually needs a coordinated seeding strategy. Avoid deleting training rows after registrations are connected, because the assignment says a training with registrations must not be deletable at the database level.

### Training JSON resource

`app/Http/Resources/TrainingResource.php` explicitly selects the JSON fields instead of returning every database column. The `full` field is calculated from whether `free_spots` is zero. `registrations_count` is the response key required by the assignment; Laravel can supply its value through `withCount('registrations')` in a query.

## Commands We Used

Run these from the `gym-api` project directory:

```powershell
php artisan migrate:status
php artisan migrate --path=database/migrations/2026_11_26_085238_create_trainings_table.php
php artisan db:seed --class=TrainingSeeder
```

`migrate:status` reports which migrations Laravel knows have run. Before Laravel has created its migration tracking table, it can report `Migration table not found`; that is expected for a brand-new database.

The `--path` option limits a migration command to the named file. It was used to create the training table without applying the unfinished registrations migration. A normal `php artisan migrate` applies all pending migrations, so coordinate before using it while the friend's migration is still a stub.

The seeder command runs one seeder class. Migrations change database structure; seeders insert sample records. They are separate jobs.

## Hiccups and Why They Happened

### SQLite file initially missing

Laravel first reported that `database/database.sqlite` did not exist. Creating the SQLite file at that exact project-relative location allowed Laravel to open it. The filename alone is not enough; it must be in the path Laravel is configured to use.

### Migration table not found

This happened before any migration had created Laravel's migration tracking table. Running the training migration created that tracking table and the `trainings` table.

### Seeder said `no such table: trainings`

The seeder tried inserting data before the `trainings` table existed in the SQLite database. Running the training migration first created the table; afterward, the seeder completed successfully.

### `migrate:fresh`

`php artisan migrate:fresh` drops all tables and recreates tables from migrations. It is destructive and can erase registrations and all other database data. It was run during setup, which is why the training migration then had to be applied again before seeding. Avoid it once valuable or shared data exists.

### Production confirmation during seeding

Laravel displayed `APPLICATION IN PRODUCTION` and asked for confirmation before seeding. This warning is controlled by the app environment, not by the SQLite filename. The seeder eventually completed after confirmation. Before future database-writing commands, check that the local `.env` uses `APP_ENV=local` and clear cached configuration with `php artisan config:clear` if the environment setting was changed.

## Next Step: Public Training List Route

First add the controller import to `routes/api.php`:

```php
use App\Http\Controllers\TrainingController;
```

Then add this route after the existing route definitions:

```php
Route::get('/trainings', [TrainingController::class, 'index']);
```

Laravel automatically prefixes routes in `routes/api.php` with `/api`, so this serves `GET /api/trainings`. The route points to `TrainingController::index()`. The next coding step after the route is to implement that method with an Eloquent query, `withCount('registrations')`, sorting, filters, and pagination, then return a `TrainingResource` collection.
